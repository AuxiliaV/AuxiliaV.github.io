Invoice Processing Automation

An AI-powered n8n workflow that reads invoice PDFs from an email inbox, extracts structured data with an LLM, validates it against business rules, and logs it to a spreadsheet — flagging anything that needs a human's attention along the way.

17 Workflow Nodes
4 Validation Checks

Project Overview

Small and mid-sized businesses commonly receive vendor invoices by email as PDF attachments. Someone on the team has to open each email, read the PDF, and manually type the vendor, invoice number, date, and amount into a spreadsheet for bookkeeping — a process that is slow, error-prone, and doesn't scale as the business grows.

This project turns that manual process into an automated pipeline: the system reads and logs every invoice on its own, and only involves a human when something looks uncertain or risky.

Objectives & Key Features

The workflow was built around four core objectives, each addressed by a dedicated check in the pipeline:

Missing Fields Catch incomplete extractions
Scanned PDFs Flag unreadable invoices
Duplicates Prevent double logging
High Amount Route for human review

Workflow Architecture

The pipeline moves each invoice through a trigger, an extraction stage, an AI structuring step, a three-branch validation chain, and finally a logging and alerting stage. A separate, linked workflow listens for failures anywhere in the main pipeline and raises an alert if one occurs.

Email Trigger (IMAP) Code (JavaScript) Extract from File Information Extractor (AI) IF / Conditional Routing Google Sheets Slack Error Trigger

Every incoming email can carry multiple PDF attachments. A Code node normalizes these into one item per invoice before anything else runs, so every later node — extraction, validation, logging — processes each invoice independently, regardless of how many arrived together.

AI-Powered Invoice Data Extraction

Extracted PDF text is passed to an LLM-backed Information Extractor node, configured with a fixed schema so every invoice returns the same structured fields.

vendor_name invoice_number invoice_date due_date subtotal tax_amount total_amount currency

Itemized line items were deliberately left out of the schema. Nested, multi-level fields are where smaller models are least reliable — the flat-field pipeline was proven solid first, with line-item extraction scoped as a future addition rather than risking silently wrong data in the first version.

Validation, Duplicate Detection & Approval Rules

Every invoice passes through four checks before it's logged. Business rules — the approval threshold, the required fields, what counts as a duplicate — are enforced in code, not left to the AI model's judgment, so they can never be reasoned around.

Invoices above a configurable Amount threshold are still logged automatically, but flagged with a need_review status and routed to a Slack alert — the pipeline never blocks a valid invoice, it just asks a human to glance at the risky ones.

Slack Notifications & Google Sheets Logging

Every invoice ends in exactly one of four outcomes, each routed to the right destination:

Auto-Logged Sheets only
Need Review Sheets + Slack alert
Duplicate Slack alert only
Invalid / Scanned Slack alert only

Testing Scenarios & Error Handling

Each branch of the workflow was tested deliberately, not just the default path — including forcing a failure to confirm the linked error-handling workflow actually fires.

Scenario Expected Behavior Result
New invoice, under threshold Auto-logged, no alert ✅ Pass
New invoice, above threshold Logged as need_review, Slack alert sent ✅ Pass
Missing required field Routed to alert, not logged ✅ Pass
Email with 2 new invoices Both processed independently ✅ Pass
1 new + 1 duplicate invoice New logged, duplicate alerted ✅ Pass
2 duplicate invoices Both alerted, neither logged ✅ Pass
Scanned / image-based PDF Routed to manual review, skips AI step ✅ Pass
Forced node failure Error-handler workflow fires, Slack alert sent ✅ Pass

Key Takeaway

Building this project meant going from zero prior Docker and n8n experience to a working, multi-branch automation pipeline with real error handling — and debugging two genuinely subtle bugs along the way, including a silent data-nesting mismatch that produced no error at all, just quietly wrong results. Tracking it down took targeted debug fields and a methodical, step-by-step process of elimination, not guesswork.
